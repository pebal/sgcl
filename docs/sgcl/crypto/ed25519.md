# sgcl::crypto::ed25519

```cpp
#include "sgcl/crypto/ed25519.h"   // or "sgcl/crypto.h"

namespace sgcl::crypto::ed25519 {
    class public_key;
    class private_key;

    inline constexpr size_t public_key_size = 32;
    inline constexpr size_t private_key_size = 64;
    inline constexpr size_t seed_size = 32;
    inline constexpr size_t signature_size = 64;
}
```

`sgcl::crypto::ed25519` is Ed25519 (RFC 8032 §5.1), Go's `crypto/ed25519`: signatures of 64 bytes under keys of 32.
The scheme is deterministic — the same key and message give the same signature, and signing needs no random
numbers — and it is the signature of SSH keys, of TLS 1.3 certificates, of package managers and of JWTs (EdDSA).
Pure Ed25519 only: the message is signed as it is, not a digest of it (Ed25519ph and Ed25519ctx are not here, as
they are not in Go's default). A [private_key](ed25519-private_key/README.md) signs, a [public_key](ed25519-public_key/README.md)
verifies.

Written from RFC 8032, it is tested against the RFC's vectors (TEST 1, 2, 3, 1024 and SHA(abc)), against OpenSSL on
messages of every length 0–1024 and a few large ones (the same signatures, each verifying the other's), against Go's
`crypto/ed25519` on two thousand random keys and the SUPERCOP vectors of Go's tree, and on the edge cases of
verification against Go and against a slow reference on big integers.

**The implementation has not been through an independent cryptographic audit.**

## Rules

- **A private key is a seed** of 32 random bytes. SHA-512 of the seed gives the secret scalar (its first half,
  clamped), the prefix the nonces are derived from (its second half), and the public key, the point A = s·B.
- **Verification is Go's and RFC 8032's**: S must be below the group order L; the public key must be the canonical
  encoding of a point on the curve; R is compared as bytes with the encoding of [S]B − [k]A, so a non-canonical R
  never matches; and the equation is the one without the cofactor. Keys of small order are not refused, as neither
  the RFC nor Go refuses them: under such a key a signature can be had for nothing, so a protocol that must bind a
  signature to one signer checks the key where it is registered.
- **Where it differs from Go and OpenSSL, deliberately.** Two things, both stricter:
  - *A non-canonical public key is refused.* An encoding of y = p or more (`ed…ff7f`, `ee…ff7f`) and an x of 0
    with the sign bit set (the "negative zero") are not points by RFC 8032 §5.1.3 ("if the resulting value is ≥ p,
    decoding fails"); Go and OpenSSL reduce them and accept the signatures under them. Of the tests' edge cases
    these two are the only ones where the verdicts differ, and the test lists them as the expected differences.
    Accepting them serves only consensus between implementations (ZIP 215), which TLS and X.509 do not need.
  - *[from_private_bytes](ed25519-private_key/from_private_bytes.md) checks the public half* against the seed, at
    the cost of one scalar multiplication; Go takes the 64 bytes as they are. A pair put together from two sources
    would sign under someone else's public key, and signatures under a mismatched pair give the secret scalar away.
- **Constant time where it matters.** Signing computes r·B for the secret nonce r by a fixed-base multiplication
  whose table is read whole with masks, and S = r + k·s mod L by arithmetic with no branch on the values; the field
  arithmetic has no branch and no memory index that depends on a value. What is secret: the seed, the scalar, the
  prefix, each signature's nonce. What is not: the public key, the message, the signature and everything the
  verification computes — the verification takes branches on them, as every implementation's does.
- **A private key is a secret, so it is not copied.** It holds the seed, the scalar and the prefix in the object's
  own memory, is move-only, and is zeroed when moved from and when destroyed; `seed()` and `bytes()` are
  [secret\<32\>](secret/README.md) and `secret<64>`, the exports [secret_bytes](secret_bytes/README.md), which zero themselves in
  turn. A key belongs on the stack or in a `unique_ptr`: in a managed object it stays in memory until the cycle that
  finds it dead.
- **Keys in files**: PKCS #8 (RFC 8410, OID 1.3.101.112, the seed inside) for the private key and
  SubjectPublicKeyInfo for the public key, byte for byte as OpenSSL writes them, and PEM, `PRIVATE KEY`, read and
  written straight into a `secret_bytes`. Reading is strict DER; another algorithm's key is `errc::unsupported`,
  broken DER `errc::malformed` with the offset. [encoding::pem](../encoding/pem/README.md) is for public PEM
  (certificates); its bytes are managed, where a private key's must not be.

| [private_key](ed25519-private_key/README.md) | a seed of 32 secret bytes and what it gives, that signs; move-only |

|---|---|---|

## Example

```cpp
#include "sgcl/crypto.h"
#include "sgcl/encoding.h"
#include "sgcl/io.h"

using namespace sgcl;

int main() {
    // RFC 8032's TEST 2: a key from a seed of 32 bytes and a message of one byte;
    // a program makes its own key with generate() and keeps the seed secret
    auto key = crypto::ed25519::private_key::from_seed(
        encoding::hex::decode("4ccd089b28ff96da9db6c346ec114e0f5b8a319f35aba624da8cf6ed4fb8a6fb"));
    auto message = encoding::hex::decode("72");
    auto signature = key->sign(message);
    println("{}", encoding::hex::encode(signature));

    // the receiver has the public key's bytes, the message and the signature
    auto received = crypto::ed25519::public_key::from_bytes(key->public_key().bytes());
    println("{}", received->verify(message, signature) ? "valid" : "forged");
    println("{}", received->verify("R", signature) ? "valid" : "forged");
}
```
