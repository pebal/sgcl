# sgcl::concurrent

Structures shared by any number of threads without a lock: the textbook algorithms with no reclamation scheme in them, because the collector is one, under the names of `std` and with the interfaces of `java.util.concurrent`; the atomic tracked pointer they are built on; a value replaced whole; a cache over the hash map. `#include "sgcl/concurrent/concurrent.h"` brings the module in; it depends on [`core`](../core/README.md) and [`containers`](../containers/README.md), and the versions of the [`im`](../containers/im/README.md) containers are published through its `copy_on_write` and `atomic`.; the index of the whole interface is [`docs/sgcl/`](../README.md); the lock-free containers against `std` under a mutex, Go and Java, in numbers, are on [benchmarks](benchmarks.md).

## Lock-free containers
`concurrent_queue<T>`, `concurrent_stack<T>`, `concurrent_sorted_map<Key, T, Compare>`, `concurrent_sorted_set<Key, Compare>`, `concurrent_map<Key, T, Hash, KeyEqual>` and `concurrent_set<Key, Hash, KeyEqual>` are structures shared by any number of threads without a lock: the Michael–Scott queue (the algorithm of Java's `ConcurrentLinkedQueue`), the Treiber stack, the lock-free skip list of Herlihy and Shavit (the structure of Java's `ConcurrentSkipListMap` and `ConcurrentSkipListSet`) and the split-ordered list of Shalev and Shavit (the resizable lock-free hash table, what Java's `ConcurrentHashMap` is for), each written as the paper has it. What a collector changes in these algorithms is everything that is not the algorithm: in C++ they come with hazard pointers, epochs or counted pointers, a reclamation scheme that decides when a node another thread may still be reading can be freed, and that scheme is where the difficulty and the bugs are. Here a node is never reused while a thread holds it, so a link is a `tracked_ptr` in an `atomic`, a compare-exchange is a compare-exchange, and a popped or unlinked node is garbage the collector reclaims. A hazard pointer exists in the library, one per thread inside `atomic::load` for the length of the load ([The classes](../core/README.md#the-classes)), and nothing in the containers or in a program using them knows of it.

- The queue and the stack are two and one atomic words; `push`, `emplace` and `try_pop` are lock-free and linearizable, `pop` waits on an empty container (the atomic's `wait`), `empty` is a load or a short walk, `size` a walk. The stack backs off exponentially after a failed compare-exchange, up to `config::BackoffMax` pauses (`-DSGCL_BACKOFF_MAX`), which is what keeps sixteen threads at one word from spending their time on retries. An element is moved out of its node by the thread that pops it and destroyed there, as `std::queue::pop` and `std::stack::pop` destroy theirs. The queue is the Michael–Scott queue in the form Java's `ConcurrentLinkedQueue` gives it: the head and the tail lag a node behind and are swung every second node, a pop claims an element with an exchange on its node's flag, and a node the head has passed is linked to itself, so that an old head a thread still holds retains nothing; the head and the tail are kept a cache line apart.
- `concurrent_bounded_queue<T>` and `spsc_queue<T>` are the bounded queues, the counterparts of Go's buffered `chan` and of Java's `ArrayBlockingQueue`: a ring of cells fixed at construction (the capacity rounded up to a power of two), one managed buffer taken once and no allocation per element, an element constructed in its cell by the push and moved out and destroyed by the pop, the cells traced by the collector so that an element holding a `tracked_ptr` keeps its object for exactly as long as it sits in the ring. The first is Vyukov's bounded MPMC queue for any number of producers and consumers: a sequence number per cell, and one compare-exchange per operation on the producers' word or the consumers'. The second is the same ring for exactly one producer thread and one consumer thread, without the compare-exchange, each side reading its own index only, so that the cell is the one line the two share: a load and a store per operation, 5.7 ns per element between two threads, what one thread pays doing both. Both have `try_push`, `try_emplace` and `try_pop`, which never wait, and `push` and `pop`, which wait for room or for an element (a spin of a few microseconds, then the kernel); `size`, `capacity`, `empty`, `full`.
- The map is a sorted bottom list holding every element, with a quarter of the nodes rising to each next level, so that a search descends from the top in logarithmic time; a node is one managed object holding its element and all its links. `insert`, `emplace`, `try_emplace` and `erase` are lock-free and linearizable, `find`, `contains`, `lower_bound` and `upper_bound` wait-free. A logical deletion is a marker node linked after the deleted one at each of its levels (Java's way of marking a link without stealing a bit from the pointer, which the pointer maps could not follow), and the next search that passes a marked node unlinks it. Iteration is weakly consistent, as Java's: an iterator holds its node by a word of the container's kind, so it is valid whatever the other threads do, it skips the elements erased since it passed them and may or may not see the ones inserted meanwhile. An erased element lives on while an iterator holds its node and dies with the node at a sweep: the one container of the library whose elements outlive their erasure, because the thread erasing cannot know who is reading. There is no `operator[]`, `at`, `insert_or_assign` or node handle.
- `concurrent_priority_queue<T, Compare>` is the one container here that is not lock-free, on purpose: a binary heap under a spin-then-park lock, what Java's `PriorityBlockingQueue` is. It was first the skip-list priority queue of Shavit and Lotan over the list of the map, and lost to every heap under a lock it was measured against, two to fourteen times per operation ([benchmarks](benchmarks.md#the-bounded-queue-the-priority-queue-intern-and-the-weak-map)): the front of a priority queue is one place every consumer writes, a lock-free structure races for its cache lines, a heap under a lock keeps them in one thread's cache at a time. The least element first, equal elements FIFO by a number the push takes, the heap a vector on the managed heap, elements moved out at the pop; a blocking `pop` waits on the count of the pushes. Go has none.
- The hash map is one sorted list holding every element, ordered by the bit reversal of its hash, with an array of buckets pointing into it at dummy nodes made on first use; the array doubles once the elements outnumber the buckets, and doubling moves no node: the old slots are copied, the rest made on use, and the old array is garbage once nothing walks it. That old array, and every node a walk may be standing on, is exactly what a reclamation scheme has to guard in C++ without a collector, and why a resizable lock-free hash table is the structure that needs one most. `find` is wait-free, `insert`, `try_emplace` and `erase` linearizable; the count is striped over cache lines (Java's `LongAdder`), `size()` its sum; iteration is weakly consistent in the order of the list. The sets are the same structures with the key as the element, the elements const.
- `concurrent_cache<Key, T>` is a cache over the hash map: bounded by a capacity and, if asked, a time to live, evicting the least recently used (Guava's `Cache`, Caffeine), the concurrent counterpart of the two-line LRU cache of `ordered_map`. A `get` is the map's wait-free search plus a relaxed store of an access stamp into the entry, never a lock and never a shared write, since an exact LRU list moved on every hit is what a cache read by many threads cannot afford; the order is approximated as Redis approximates it, every entry stamped with a clock the insertions tick, and the thread whose `put` took the size past the capacity evicts the oldest of a sample of eight ([concurrent_cache](concurrent_cache.md)).
- `copy_on_write<T>` is the simplest of them and the one C++ has needed longest: a value read on every request by many threads and changed once in a while by one, a configuration, a routing table, a list of listeners. `load()` is one atomic load and gives a snapshot, a pointer to `const T` that stays what it is, and alive, for as long as it is held; `update(f)` copies the value, applies `f` to the copy and swings the pointer with a compare-exchange, and the old value is garbage once its last snapshot is dropped. That is the whole of RCU, and of every `shared_ptr` swapped under a lock, with the one question those exist for, when the old value may be freed, answered by the collector.
- `channel<T>` is the channel of Go: a queue with the synchronization of both ends. A channel of capacity *n* buffers *n* elements, one of capacity 0 buffers none and a send waits until a receive takes the element (a rendezvous); a receive on an empty channel waits, a send on a full one waits, so a producer ahead of its consumer stops; `close()` ends the stream, what was sent still received and then nothing. The waiting side is a thread, on an atomic of its own, or a coroutine: `co_await ch.async_receive()` suspends a `task<T>` with its handle on the channel's list of waiters, and the send that serves it hands it to the scheduler ([Coroutines](../async/README.md#coroutines)), which runs it on a worker. The buffer is a lock-free ring (Vyukov's bounded queue: a slot with a sequence number each, one compare-exchange per operation, no allocation per element), the lists of waiters are `concurrent_queue`s and every waiter is a managed object: no lock anywhere, and a waiter served or cancelled is the collector's. A `channel<void>` carries signals. `select` is the wait on several channels at once, the select of Go: a receive or a send per case with a body, `otherwise` for the case taken when nothing can be served (a poll), for a thread (`select(...)`) and for a coroutine (`co_await async_select(...)`); it takes no lock either: one waiter per channel sharing one state, the channel that serves a case winning it by a compare-exchange, the rest dead entries the collector reclaims ([select](../async/select.md)).
- `concurrent_weak_map<Key, T>` and `concurrent_weak_set<Key>` are the [weak containers](../containers/README.md#weak-containers) shared by any number of threads: keyed by the identity of objects held weakly, over the hash table above, so that metadata attached to objects, a cache keyed by the object or a registry of instances is shared by the workers and forgets an object when its owner drops it (Java's `WeakHashMap`, which has no concurrent form; here it is the split-ordered list with weak keys). An entry whose object a cycle has found unreachable is dead: never found, passed over by a walk, and swept out by the inserting thread whose insertion brings the count since the last sweep to as many as the container has entries, one sweep at a time and none waiting, so that an insertion stays lock-free; the sweep is safe under the threads because the collector clears a weak cell before the object's slot can be handed out again, so an entry seen dead is dead for good. An entry carries the hash it was placed with, the address being gone with the object.
- `intern<T>` is Go's `unique` package and Java's `String.intern`: a pool where equal values share one managed object, `make(value)` the canonical object of the value, made and entered when none is alive, so that a program holds one copy of each distinct value and compares two in one word. The entries are the weak entries above, placed by the hash of the contents and compared through the live object, and the pool keeps nothing alive: an object dropped by everyone is collected, and the next `make` of its value makes a new one. For `string` the interned string is the string itself, since a string is one word to an object never modified: `intern_string(view)` hands back a `string`, a view or a literal interning with no string made when the value is known.
- A container lives where a `tracked_ptr` may, on a stack or inside a managed object; the structures a whole program shares go into one managed object under a `root_ptr`, a global (the default pool of `intern<T>`, `intern<T>::pool()`, is one). Iterators of the maps and sets, and the snapshots of a `copy_on_write`, are `tracked_ptr`s and live where their container may.

```cpp
struct Server {                                             // what every thread shares, in one managed object
    concurrent_sorted_map<int, tracked_ptr<Session>> sessions;
    concurrent_queue<tracked_ptr<Request>> requests;
    copy_on_write<Config> config;
    channel<tracked_ptr<Request>> inbox{64};    // a channel: producers wait when it is full
};
static root_ptr<Server> server = make_tracked<Server>();   // a global: a root

// any thread
auto [it, fresh] = server->sessions.try_emplace(id, make_tracked<Session>());
server->requests.emplace(make_tracked<Request>(id));
// a worker
while (auto r = server->requests.try_pop()) {
    if (auto s = server->sessions.find((*r)->id); s != server->sessions.end()) {   // s holds the node: valid even if erased meanwhile
        s->second->handle(*r);
    }
}
server->sessions.erase(id);   // marked, unlinked by the next search; the Session dies when nothing holds it
auto c = server->config.load();                            // a snapshot: one load, immutable, alive while c is
server->config.update([](Config& x) { ++x.generation; });  // a copy, changed, swapped in; the old one dies with its last snapshot

task<> worker() {
    while (auto r = co_await server->inbox.async_receive()) {   // the coroutine sleeps on the channel, resumed by a send
        handle(*r);
    }
}
```

The containers are measured against `std` under a mutex, Go and Java in [the benchmarks](benchmarks.md).
